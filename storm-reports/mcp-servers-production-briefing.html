How Big Tech Runs MCP Servers in Production

Architecture, security, and operations of Model Context Protocol servers at Anthropic, OpenAI, Google, Microsoft, AWS, Salesforce and peers — mined as a blueprint for building your own.

60-Second Summary

The settled part: MCP won the AI-integration standard war — adopted by OpenAI, Google, Microsoft, AWS and Salesforce, and donated by Anthropic to the Linux Foundation's Agentic AI Foundation on December 9, 2025. But no major vendor runs an MCP server the way the early demos implied. In production, MCP is a thin, stateless, OAuth-fronted façade over an existing API, behind a managed gateway (AWS Bedrock AgentCore, Cloudflare's remote-MCP stack, Copilot Studio connectors), with ruthless tool curation and per-user scoped tokens.

The settled threat model: the dominant risk is not vulnerable server code — measured vulnerability rates in open-source servers are single-digit percentages. It is model-side instruction-following (tool poisoning succeeds 36.5% of the time on average in the peer-reviewed MCPTox benchmark, and more often on more capable models) plus broken auth implementations (a 2026 measurement found flaws in 100% of the 119 OAuth-enabled remote MCP servers it audited). Every name-brand incident — Asana's cross-tenant leak, GitHub's prompt-injection exfiltration, Supabase's database exposure — broke at tenant isolation, token scope, or injected instructions, never at the protocol's cryptography.

The contested part: whether the vendor playbook is a genuine solution (the practitioner view), liability transfer for an architecturally unsolved injection problem (the skeptic view), or a toll-booth business model dressed as security guidance (the economist view). All three readings agree on what to build; they disagree on what it guarantees.

Key Findings — ranked by reliability

1. The threat is the model, not the server: tool poisoning and broken auth dominate MCP risk

9/10

The peer-reviewed MCPTox benchmark (AAAI-26) ran tool-poisoning attacks against 20 LLM agents on 45 live MCP servers with 353 authentic tools: average attack success was 36.5%, the best-refusing model refused under 3% of the time, and — critically — more capable models were more susceptible, because the attack exploits instruction-following itself (o1-mini: 72.8%). A 2026 measurement of 7,973 live remote MCP servers found 40.6% expose tools with no authentication, and of the 119 OAuth-enabled servers audited, 100% had at least one auth flaw (325 total; the work yielded 9 CVEs). Meanwhile, static analysis of 1,899 open-source servers flagged only ~7.2% with conventional vulnerabilities (detections, not confirmed exploits). The risk concentrates in the model layer and the auth layer — not in exotic server bugs.

Supported by: Academic (peer-reviewed + verified measurements), Skeptic (incident pattern), Practitioner (confused-deputy focus) Challenged by: vendor narrative that newer/more-aligned models reduce risk — the measured effect is inverted

2. Every name-brand production incident broke at the same three joints: tenant isolation, token scope, injected instructions

9/10

Asana's MCP server exposed data across roughly 1,000 customer organizations via a tenant-isolation logic bug — exposure ran May 1 to June 4, 2025, and the feature was pulled for about two weeks. GitHub's MCP server let a poisoned public issue steer an agent into exfiltrating private-repo data (Invariant Labs, May 2025), because the agent's token had more reach than the task needed — a demonstrated "toxic agent flow" that worked even on frontier models. Supabase's MCP setup leaked SQL data when a support-ticket injection met a service_role connection that bypasses row-level security (General Analysis, July 2025). The supply chain is also live: the rogue postmark-mcp npm package silently BCC'd every sent email to an attacker (Koi Security, Sept 2025 — the first documented malicious MCP server in the wild), and mcp-remote (CVE-2025-6514, CVSS 9.6, 437,000+ downloads at disclosure) allowed RCE via a malicious server's OAuth metadata. None of these were protocol-level flaws; all were scope, isolation, and trust failures.

Supported by: Skeptic, Practitioner, Academic — same incidents cited independently; all five verified against primary sources Challenged by: Academic base rates — headline incidents do not make the ecosystem a "malware swamp" (~7% measured detection rate)

3. The converged production architecture is a managed gateway over a boring API — nobody at scale hand-rolls the MCP layer

8/10

AWS Bedrock AgentCore Gateway converts existing APIs, Lambda functions, and services into managed MCP-compatible tools; Cloudflare's workers-oauth-provider plus Durable Objects (one per client session) is a flagship remote-MCP hosting stack; Microsoft exposes MCP through Copilot Studio connectors; Anthropic distributes vetted integrations through a curated connectors directory with enterprise identity provisioning. The pattern in every case: the vendor's own engineers write ordinary API/tool code, and a hardened shared layer speaks MCP, handles OAuth 2.1 token custody, and enforces per-user scoping. The MCP server itself is deliberately thin and stateless.

Supported by: Practitioner (vendor docs, all verified), Historian (matches the plugin→curated-store cleanup pattern), Economist (that's where the revenue pools) Challenged by: Skeptic — gateways do not fix in-band prompt injection; Economist — the blueprint doubles as a toll booth

4. The spec is converging on stateless + stricter auth — and it breaks things on the way

8/10

The MCP specification's 2026-07-28 release candidate (pre-announced with a ten-week validation window; final publication July 28, 2026) removes the initialize handshake and the Mcp-Session-Id header entirely — the protocol goes stateless, ending the sticky-routing and shared-session-store contortions that made horizontal scaling painful (Microsoft documented the Azure App Service scaling win directly). HTTP+SSE transport has been deprecated since spec version 2025-03-26 in favor of Streamable HTTP, with vendor cutoffs landing through mid-2026 (Atlassian dropped it June 30, 2026). Auth is now mandatory OAuth 2.1 with RFC 8707 resource indicators and audience validation. Governance moved to the Linux Foundation's Agentic AI Foundation in December 2025. For a builder this cuts both ways: the direction is clear (stateless, strict auth), but the spec ships breaking changes roughly every six to twelve months, and major clients (Cursor, Claude, VS Code) weren't even requesting refresh tokens — an interoperability gap the project had to formalize guidance for (SEP-2207).

Supported by: Practitioner and Skeptic citing the same primary spec sources — all six spec claims verified against modelcontextprotocol.io Challenged by: Skeptic's framing — a spec this young in churn means "how the majors do it" is a moving target

5. Context economics is a first-order design constraint: tool definitions are expensive

7/10

Atlassian's engineering measurement found GitHub's official MCP server exposes 94 tools consuming roughly 17.6k tokens of definitions per request, and that combining several large servers easily spends 30k+ tokens before any work happens. Anthropic's own mitigation — executing code against MCP tools loaded on demand rather than stuffing every definition into context — cut a 150,000-token workload to 2,000 tokens (a 98.7% saving, per Anthropic's engineering post, verified verbatim). The operational lesson from every vendor: curate tools ruthlessly, keep schemas terse, and treat tool-count as a budget, not a feature list. (Both figures are single-vendor engineering measurements without published formal methodology — hence the mid confidence.)

Supported by: Practitioner (operator data, primary sources verified), Economist (token consumption is the revenue engine — vendors measure it precisely) Challenged by: no lens disputed the direction, but the figures are vendor self-measurements, not audited benchmarks
Hidden connection

The link across all five lenses

Every lens independently converged on the same choke point: the intermediary layer. The practitioner says gateways solve auth and sessions. The academic says fixes must be architectural — deterministic controls outside the model, because the model's susceptibility rises with capability. The historian says permissive plugin ecosystems always get re-architected into curated, sandboxed intermediaries after the security disasters (ActiveX → extension stores), and that protocols live or die by the default client. The economist says the money pools exactly there — metered gateways, token consumption, curated registries. In other words: the security architecture and the market structure are the same diagram. Whoever owns the interposition layer collects both the safety guarantees and the rent. For a builder, the gateway is not overhead to minimize — it is the strategic ground the entire industry is fighting to occupy.

Key assumption · missing 6th lens

What no lens addressed

The insider operator and the regulator. Every lens worked outside-in: public docs, incident disclosures, registry scans, academic measurements of open servers. There is no independent evidence about how Anthropic, Google, or AWS actually operate MCP internally — SLOs, monitoring, red-team cadence, incident response — so "how the majors do it" is really "what the majors publish." (Even Asana never issued a public disclosure; the record exists only because customers shared their notification emails.) And no lens addressed liability: when an agent leaks cross-tenant data through an MCP chain, is the server operator, the client vendor, or the model provider legally responsible? EU AI Act enforcement and data-protection rulings could redistribute that liability onto server operators — which would flip the economics of running one. This briefing's conclusions assume the published architecture reflects the practiced one, and that the liability regime stays vague. Both assumptions are unverified.

Actionable Insight — for an engineer building a production MCP server

  1. Do not hand-roll the auth/session layer. Put your tools behind a managed layer (Cloudflare's workers-oauth-provider, AWS AgentCore Gateway) or implement OAuth 2.1 with RFC 8707 resource indicators exactly to spec. 100% of the 119 audited DIY OAuth deployments had at least one flaw — assume yours will too unless it's boring, borrowed, and tested.
  2. Design stateless from day one. The spec version finalizing July 28, 2026 deletes sessions and the handshake entirely. Any sticky-session or shared-session-store infrastructure you build now is scheduled for demolition. Thin, stateless MCP façade over your real API.
  3. Make tenant isolation your #1 test surface. Asana's leak was a logic bug, not a hack. Write cross-tenant access tests, scope every token to the calling user (never a service-role or broad PAT), and verify isolation on every tool path before launch.
  4. Assume prompt injection succeeds and design so it doesn't matter. Default tools to read-only, require human confirmation for destructive or outbound actions, and restrict egress — break the "lethal trifecta" (private data + untrusted content + exfiltration channel) structurally, because no model refuses reliably (<3% refusal in the peer-reviewed benchmark).
  5. Treat tool-count as a token budget. Curate to the minimum viable toolset, keep schemas terse, and for large tool surfaces consider the code-execution-over-MCP pattern instead of loading every definition into context.
  6. Build to the strictest client's bar and pin spec versions. Protocol history says the default client's policy becomes the de facto spec. Track the official MCP blog and SEP changelog for breaking changes; the spec has broken things roughly every six to twelve months.

Contested Signal

Ecosystem vulnerability rates conflict by methodology, not by facts. Endor Labs (82% path-traversal-prone file ops, 34% command-injection-prone APIs, n=2,614) measured risk-prone API usage; Equixly (43% command injection) ran penetration tests on an undisclosed sample; the arXiv study (7.2%, n=1,899) counted static-analysis detections. These are three different instruments — secondaries routinely merge them into one scary number. None is comparable to another.

OX Security's "~200,000 vulnerable deployments" (April 2026 stdio advisory) is OX's own estimate from a companion post; the downstream CVEs were assigned to third-party products (LiteLLM, Windsurf, Flowise…), and Anthropic responded that the SDK behavior is by design. Real advisory, contested framing.

Frontier question

The one question that would change everything

Can deterministic architecture — gateways, scoping, egress control — hold the line indefinitely against a model layer whose injection susceptibility rises with capability, or does safe tool use ultimately require solving in-band prompt injection at the model level, which no vendor has done?
